# AI Commerce OS 2608·V2 信息架构（Information Architecture）

状态：初稿，待 Founder 确认。

本文件重新设计一级/二级导航，**不参考、不复制** V1 导航（`frontend/src/console/nav/navConfig.js` 及
`docs/workspace-page-mapping.md` 中的 founderWorkspaceGroup / aiCapabilityCenterGroup / operatorLabGroup 等分组）。
V2 导航以第二份文档《领域模型》中的对象为依据重新划分，与 V1 的模块名称、分组方式没有继承关系。

## 1. 一级导航（10 项）

| 顺序 | 一级入口 | 对应主体 | 一句话定位 |
|---|---|---|---|
| 1 | **SinoFUT** | 智能入口 | 系统唯一秘书，对话驱动一切 |
| 2 | **经营驾驶舱** | Founder | 今天的机会/生产/经营/流量/利润/能力升级 |
| 3 | **增长网络** | Growth | 发现机会、建设流量资产 |
| 4 | **内容生产网络** | Studio | 无限画布生产内容资产 |
| 5 | **经营中心** | Operator | 店铺/商品/客户/广告/订单/利润的真实经营 |
| 6 | **能力中心** | 能力层 | Agent/Prompt/Skill/Workflow/Knowledge/Connector/Capability 的研发与版本管理 |
| 7 | **Marketplace** | 生态层 | 已验证能力/内容/服务的交易市场 |
| 8 | **Operator Cloud** | 生态层 | Operator 部署实例的设备/版本/许可证/AI经营额度/远程运维管控层 |
| 9 | **数据中心** | 治理 | 跨主体的经营数据与分析 |
| 10 | **系统管理** | 治理 | 账户、权限、Connector 鉴权、系统配置 |

**导航即身份**：第 2-5 项分别对应 Founder 的四个身份中的"经营者/创始人"视角切入点；SinoFUT（第1项）是唯一贯穿全部身份的入口，其余入口是 SinoFUT 之外的"手动直达"通道，二者调用同一套能力层，不是两套系统。

## 2. 各入口详细结构

### 2.1 SinoFUT（智能入口）

- **交互范式**：单一自然语言输入框 + 上下文卡片流，不设传统二级菜单。
- **构成**：对话区、任务规划区（当前排队中的 Task）、Agent/Workflow 调用回执、待审批（Approval）浮层。
- **对象**：Memory、Task、Approval、跨主体调用回执。

### 2.2 经营驾驶舱（Founder Cockpit）

- **交互范式**：驾驶舱式仪表盘，围绕六个每日问题组织，而非菜单式后台。
- **二级结构**（对应宪章十二的六问）：

| 二级入口 | 回答的问题 | 关联对象 |
|---|---|---|
| 今日机会 | 今天有什么机会？ | Opportunity |
| 今日生产 | 今天生产什么？ | Content、Strategy |
| 今日经营 | 今天经营什么？ | Product、Store、Order、Task |
| 流量来源 | 流量来自哪里？ | Campaign、Ad、Customer（私域） |
| 今日利润 | 利润是多少？ | Profit |
| 能力升级 | 哪些能力需要升级？ | Capability、Version、验证闸门状态 |

- **四身份切换**：驾驶舱顶部提供身份视角切换（创始人/经营者/内容生产者/增长验证者），切换后同一份数据以不同关注点重排，不是四个独立页面。

### 2.3 增长网络（Growth）

- **交互范式**：发现信息流（机会雷达）+ 资产网络图（流量池/私域/渠道关系）。
- **二级结构**：机会雷达（Opportunity）、内容矩阵总览（引用 Studio 的 Content）、私域资产、达人网络、渠道网络、活动（Campaign）管理、向 Operator 的流量交付看板。

### 2.4 内容生产网络（Studio）

- **交互范式**：**无限画布（Infinite Canvas）**，是宪章第九条明确规定的唯一形态，禁止传统后台式页面。
- **二级结构（画布内的功能面板，而非独立页面）**：素材库、分镜/脚本管理、图文生产流、视频生产流、AI 短剧生产流、数字人管理、品牌 IP 资产、Studio 自有矩阵账号与收益（广告收益、版权收益）。
- **产出通道**：画布内容可一键"交付给 Operator"或"发布到 Marketplace"。

### 2.5 经营中心（Operator）

- **交互范式**：经营操作队列 + 结构化数据表（这是系统中唯一大量使用表格的区域，因为经营本身需要精确的结构化数据）。
- **二级结构**：店铺管理（Store）、商品管理（Product）、客户与私域（Customer）、广告投放（Ad，含从 Growth/Marketplace 购买的流量）、订单履约（Order）、客服、利润与结算（Profit）、内容采购（来自 Studio/Marketplace 的 Content）。

### 2.6 能力中心（Capability Center）

- **交互范式**：资产管理 + 编辑器（Agent/Prompt/Skill 有专属编辑态，Workflow 用编排画布）。
- **二级结构**：Agent 中心、Prompt 中心、Skill 中心、Workflow 编排、Knowledge 中心、Connector 中心、Capability 目录（含验证状态与晋升审批入口）、Version 历史。

### 2.7 Marketplace

- **交互范式**：目录浏览 + 详情页，面向"已验证能力/内容/服务"的交易场景。
- **二级结构**：能力市场（Capability）、内容市场（Studio 内容授权）、流量与增长服务（来自 Growth，本轮修订后由此承载，见 [07-foundation-review.md](07-foundation-review.md)）、服务市场（第三方/Operator 间的服务）、上架管理（Founder/Studio 侧）、采购记录（Operator 侧）。

### 2.8 Operator Cloud

本轮修订：Operator Cloud 不再是"流量/内容订阅目录"（该职责移至 2.7 Marketplace），而是 **Operator 部署实例的设备、版本、许可证、AI 经营额度与远程运维管控层**，对应 [02-domain-model.md](02-domain-model.md) 4.1 节的 Device/License/AIQuota 对象。

- **交互范式**：设备/实例列表 + 状态卡片，密度介于经营中心与系统管理之间。
- **二级结构**：设备状态、系统版本与升级、许可证管理、人工智能经营额度（额度余量/告警）、故障与远程运维工单、脱敏运行指标（不展示 Operator 的订单/客户/聊天/利润明细，见首页设计禁止项）。

### 2.9 数据中心

- **交互范式**：分析视图（图表为主，不做表格墙）。
- **二级结构**：全局经营看板（跨 Growth/Studio/Operator 汇总）、机会验证追踪、利润归因、能力使用效果分析。

### 2.10 系统管理

- **交互范式**：标准设置页（系统中唯一允许"传统后台风格"的区域，因为这里服务的是配置而非经营）。
- **二级结构**：账户与权限、Connector 鉴权管理、Approval 规则配置、品牌/店铺主数据管理、系统日志。

## 3. 导航设计原则

1. **对话优先，菜单其次**：SinoFUT 不是十个入口之一，而是可以从任意入口唤起的悬浮层，十个一级入口是"菜单化的 SinoFUT 能力子集"。
2. **一级导航数量固定为 10**，不因后续页面增多而膨胀；新能力优先通过 SinoFUT 对话或已有入口的二级结构承载。
3. **禁止出现"实验室/中心"式的模糊分组**（如 V1 的"Operator 实验室""AI 能力中心"）：每个一级入口对应一个在架构文档中明确定义的主体或治理层，边界清晰可解释。
4. **Studio 强制无限画布，经营中心允许表格**：不同主体允许不同的信息密度，取决于其工作本质（创作 vs 精确执行），不强求全系统统一交互范式。
5. **Founder 驾驶舱不是"更大的后台"**：即使数据来自四个身份的全部活动，呈现形式必须保持"六问驾驶舱"的克制结构，不允许退化为菜单聚合页。
