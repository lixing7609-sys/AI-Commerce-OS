## 3. 新增收入口径核对

V2-001 任务第四条列出九类持续收入（设备与部署/系统许可/AI经营额度/内容服务/增长与流量服务/广告服务/能力商城/Operator Cloud服务/远程运维）。05 号文档原第2节利润来源表只覆盖其中约五类，且未显式列出"设备/许可证/AI额度/远程运维"四类（因为原 Operator Cloud 定义本身就不含设备管理）。

**已修订**：05 号文档新增 2.1 节"持续收入九分类"，逐一映射到归属主体与领域对象，与第4项的 Operator Cloud 定义修订联动。

## 4. 尚未解决但不阻塞开发的问题

以下问题记录在案，留待后续迭代，**不阻塞本轮进入代码阶段**：

1. **Tenant 的落地粒度尚未定义**：当前只定义了 Tenant 对象存在，但"一个 Founder 本人算不算一个 Tenant""未来一个 Operator 客户是否等于一个 Tenant"的具体划分规则留待 Phase 6 之后、真正引入第二个使用者时再细化。第一阶段代码中 Tenant 先以"单租户（Founder 自己）"为默认值实现，接口保留多租户扩展点。
2. **AIQuota 的计费单位与定价**尚未确定（按 token、按 Agent 执行次数、按 Workflow 次数三种口径均有可能），本轮先以"额度余量百分比"的展示形态占位，具体计价规则留待接入真实模型调用成本后再定。
3. **Marketplace 与 Operator Cloud 的服务市场边界**在小范围场景下可能重叠（例如"内容以额度形式订阅"到底算 Marketplace 交易还是 Operator Cloud 服务），第一阶段以第4项修订的划分为准，出现真实业务场景冲突时再修订。
4. **Studio/Growth 是否会有独立 App**：V2-001 任务第十一条只列出 apps/founder、operator、studio、operator-cloud 四个独立工程，Growth、Marketplace、数据中心、系统管理未被列为独立 App。本轮审查决定：Growth/Marketplace/数据中心/系统管理作为 Founder App 内的工作区实现（因为它们服务于 Founder 的孵化职能，不是独立对外销售的产品），Operator/Studio/Operator Cloud 三者才是未来可能独立部署销售的产品，因此需要物理隔离的独立工程。此决定记录在此，后续如需拆分 Growth 为独立 App，需重新评审。

## 5. 结论：是否允许进入代码阶段

**允许**。以上十项检查中，构成真实冲突的仅第 2/4/5/7/8 项相关的 Operator Cloud 定位与多租户权限问题，均已通过修订 01/02/03/05 号文档解决，不属于 V2-001 任务第二十二条列出的六种暂停情形（无商业逻辑无法自行解决的冲突、无需删除/覆盖 V1 数据、无需修改已冻结的品牌或主体边界之外的内容、无高成本不可逆基础设施引入、无需使用真实账号/资金/发布权限、当前仓库技术结构可以合理建立 V2 隔离工程）。

进入 Phase 5/6 代码阶段前，最终基线文档清单：01～06（已修订）+ 07（本文件）。08 号后端审查文档将在代码阶段同步产出，不影响本次放行结论。
